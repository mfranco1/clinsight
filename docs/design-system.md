# Design system and UI conventions

## Visual foundation

Clinsight uses Tailwind CSS v4, semantic CSS variables in `src/styles/tokens.css`, shared React primitives, Lucide icons, Motion, and Radix Dialog, Select, Popover, and Dropdown Menu behavior. `src/styles/globals.css` imports the token and Tailwind layers and owns global typography, scrollbars, and motion helpers. `index.html` loads Inter.

The light theme defines canvas, surface, content, border, action, focus, clinical status, radius, and card-shadow tokens. Tailwind exposes them as utilities such as `bg-canvas`, `text-content-primary`, `border-border-default`, `bg-action`, and `rounded-control`. Semantic color ramps preserve the previous Tailwind values under Clinsight names (`neutral`, `action`, `danger`, `critical`, `warning`, `info`, `pending`, `success`, `attention`, and `accent`), so existing clinical/status distinctions remain stable while their values are centrally managed. Application JSX no longer uses the former palette names. Use semantic utilities for all new or changed UI.

Spacing and typography use Tailwind's shared spacing and type scales; do not add one-off values when an existing scale fits. Use the semantic radius and shadow tokens for shared controls and cards. Workflow-specific dimensions remain local where they express layout constraints rather than design language.

Clinical information must remain readable and statuses distinct. Preserve meaningful medical formatting, numbers, and units in editable text, Markdown, print, and clipboard views. `src/components/ui/RichContent.tsx` owns generic safe rendering for plain text, Markdown, and explicit HTML fragments; `src/components/clinical/ClinicalMarkdown.tsx` adds clinical references, citations, and search decoration. Markdown supports GFM, KaTeX math, and a sanitized semantic HTML subset. Footnote syntax is outside the GFM contract and remains literal text. Source disclosure is opt-in so ordinary displays do not repeat their content. HTML is sanitized before rendering, generated element IDs are scoped, links are restricted to safe schemes, and images render as alt text to avoid remote requests. Do not preprocess and persist display content or use raw HTML injection.

## Component ownership and reuse

- Generic controls belong in `src/components/ui/`. Use `Button`, `Badge`, `TextInput`, `TextArea`, `FieldLabel`, status selectors, toolbar controls, file-upload controls, and empty states where their contracts fit.
- Shared dialogs live in `src/components/dialogs/` and compose through `ModalShell`. Dialog focus and close behavior use Radix Dialog. `ModalShell` supports a title or explicit accessible name, an optional description, center, bottom-sheet, or right-drawer placement, safe-area spacing for bottom sheets, explicit Escape/outside-interaction close policies, and an optional feature-owned overlay class for established visual needs. `ConfirmationModal` forwards the dismissal policies for workflows that require an explicit button choice. Preserve existing defaults and choose dismissal policy per workflow. Status selectors use Radix Select, while order and medication status meanings remain in their feature/domain adapters.
- Use `src/components/ui/DropdownMenu.tsx` for actions attached to a trigger. It provides shared brand styling and Radix menu keyboard/focus behavior, portal positioning, viewport collision limits, and typed default/destructive item variants. Keep menu items to actions; use `Popover` for checkbox/form content and Radix Select/native select for choosing one value. For menus inside a modal, raise the content layer above the dialog deliberately and verify focus dismissal/return in the composed surface.
- Use `src/components/ui/Popover.tsx` for anchored non-menu content such as input template/history lists and chart section controls. A popover is not an action menu: preserve its appropriate dialog semantics and keep complex controls as regular form elements.
- The selection-relative deep-dive composer in `PatientNoteCard` remains feature-owned: its position follows the selected text, it contains the chat composer and recording state, and its dismissal policy accounts for nested dialogs. Do not replace it with a generic action menu or reposition it without preserving those interactions.
- Clinical Markdown and chat input live in `src/components/clinical/`; keep source references and clinical workflow semantics there. Generic content parsing and rendering belongs in `src/components/ui/RichContent.tsx`.
- Feature-specific views and components stay under their owning `src/features/` directory. Shared controls accept typed values and callbacks rather than clinical workflow decisions.
- Navigation and application chrome belong in `src/app/shell/`.
- `ViewNavigationItem` in `src/components/ui/` shares current-page semantics and item layout between the desktop sidebar and mobile bottom navigation. Keep view lists, navigation state, and navigation callbacks in `app/shell/` and `App.tsx`.
- `BottomActionBar` is a nonmodal, named action group for view-scoped bulk actions. Use `ModalShell` for bottom-sheet dialogs; an action bar must not trap focus or block the underlying workflow.
- Chart smart append uses `ModalShell` with bottom-sheet placement on narrow screens and a centered dialog at larger breakpoints. Dictation, draft content, merge behavior, and cancellation stay with the chart feature.
- `ResponsiveTableSurface` provides a labelled, horizontally scrollable frame for feature-owned responsive records. Its role is a named region; it does not claim ARIA table/grid semantics. Keep row editing, grouping, selection, and keyboard behavior with the owning feature until a complete table interaction model is implemented.
- Multi-control popovers remain distinct from action menus. The chart section manager uses labelled accordion buttons with expanded state and contextual “Show all”/“Hide all” checkbox actions; preserve its per-entry visibility owner and do not give it menu keyboard semantics.

Existing composable foundations serve multiple workflows: `SectionCard` is shared by chart and profile; `StickyToolbar` and `ToolbarButton` serve input, chart, notes, orders, course, and handoff; `DateRangeFields` serves chart and notes; `EditableTextArea` serves chart, input, orders, course, and handoff; and `StatusDropdown` backs separate order and medication adapters. `ToolbarButton` forwards native button props so Radix triggers can compose through `asChild`; give icon-only actions an explicit accessible name. Prefer these contracts over new feature-local copies. Keep their domain-specific semantics in the owning adapters.

Long patient-note, chart-section, course-detail, and handoff-summary editing use `EditableTextArea` with the `DocumentTextEditor` composition. It offers visual, source, and rendered-preview modes. Visual conversion is enabled when Markdown round-trips to the same schema content; table-only spacing/alignment normalization is accepted only when reparsing yields the identical document tree and non-table source remains unchanged. Untouched values remain the original string; an intentional table edit can serialize canonical table spacing. Unsupported HTML, math, and other schema content stays in source mode. The visual editor uses Tiptap/ProseMirror and its Markdown bridge, which is currently Beta; keep the fidelity gate until richer syntax has explicit round-trip coverage. Its toolbar supports emphasis, links, ordered/unordered/task lists, block quotes, headings, and table operations. On narrow screens the mode switch stays visible and the touch-sized formatting toolbar scrolls horizontally. Rich HTML paste keeps supported text formatting and table structure, strips active content and event/style attributes, rejects unsafe link schemes, and converts images to their alt text without fetching or attaching them. Plain-text paste follows the editor's text path. CodeMirror powers source mode and is loaded when that mode is opened. If a lazy editor fails to load or render, an error boundary retains the current draft in a labelled plain-text editor. New-patient narrative, line-oriented plan fields, general-management fields, smart append, bulk-order syntax, order and medication notes, SOAP references, and home-instruction follow-up use CodeMirror source mode. Print generation replaces its editor chrome with the exact visible text. Chat composers, prescription instructions, one-line home-instruction recommendations, and compact inline exam fields keep their tailored/native controls.

See [architecture](architecture.md#repository-ownership) for module ownership. Promote an abstraction when multiple consumers need the same behavior; keep feature-specific detail local. Do not introduce a second component suite or replace unique clinical workflow semantics with generic flags.

## Application branding

`src/config/brand.ts` owns the readonly `BRAND` display name (`Clinsight`), tagline, C/S SVG geometry, flat light/dark palette, and derived browser icon URLs. Use `BRAND.name` for string-only labels and attribution; use `BrandName` for inline JSX prose. Do not copy app-name literals, SVG paths, or encoded icon URLs into consumers. The mark is a pair of round-capped 40-unit strokes in a `0 0 224 240` viewBox, with a 32-unit transparent circular cutout around a 20-unit teal center dot. Keep its geometry and paint roles in this definition.

Product identity components live in `src/components/brand/`. `Brand` supports `variant="full" | "icon" | "wordmark"`, horizontal/stacked layouts, `theme="light" | "dark"`, and `colorMode="full" | "mono"`. Its size presets are `sm` (32 px icon, 20 px wordmark), `md` (40/26), and `lg` (80/40). A positive numeric size is the icon viewport height for icon/full and the font size for wordmark; invalid numbers fall back to the medium preset. Numeric full lockups scale their wordmark to 65% of icon height horizontally or 50% stacked. `className` applies to the outer element; mono uses its inherited `color`. The icon variant has the accessible name `Clinsight`; a full lockup's SVG is decorative because visible text names it. The wordmark uses Inter 700, `-0.04em` letter spacing, and visible title case. `nameAs="h1"` is reserved for the login page heading. `BrandMark` is decorative by default. SVG masks use unique React IDs; preserve their transparent cutout and round terminals. Do not add backgrounds, shadows, filters, or gradients to the mark. Spinner, motion, cancellation, and navigation behavior remain in consumer workflows.

Vite's `transformIndexHtml` uses `src/config/brandHtml.ts` to populate the title, full-color SVG favicon, startup mark, and startup label in development and production before React loads. Notification icons use the full-color SVG and badges use its monochrome variant; caller overrides remain supported. The startup screen retains minimal inline CSS so it can render while the bundle is pending; its styles are the pre-CSS presentation exception, not a second logo/name definition. Standalone SVG exports use concrete palette colors; the mono component uses `currentColor`. Keep the light/dark setting scoped to the brand lockup and use monochrome for print/forced-colors contexts where appropriate. Do not add separate runtime font downloads; outlined print wordmarks must be generated from the actual Inter font and visually checked.

Branding changes do not rename storage keys, export filename prefixes, diagnostic prefixes, package identifiers, test-mode constants, or internal URL bases. Editable clinic identity and contact/account addresses are separate from product identity.

## Interaction and accessibility

Use native form elements for simple controls and Radix primitives for complex dialogs and selectors. Keep controls labelled and operable by keyboard. Verify dialog focus entry/restoration, Escape, selector arrow-key navigation and selection, focus visibility, and overlay dismissal. Radix provides behavior foundations; it does not supply the application’s visual design or guarantee that compositions are accessible.

Preserve accessible names, form labels, dialog roles, close behavior, keyboard interaction, existing feedback, and desktop/mobile layouts when changing shared controls. Keep menus and overlays within the viewport. Check affected paths on desktop and mobile with the offline browser suite.

Keep loading, error, confirmation, and empty states clear and consistent with the owning workflow. AI-generated suggestions and clinical content must remain reviewable and editable through existing flows. `LoadingFeedback.tsx` owns branded app loading, compact indicators, skeleton shapes, and shared error presentation; feature modules own their operation labels, retained content, safe user-facing messages, retries, and cancellation. `ErrorState` supports section, inline, and page presentation while preserving its section default; inline errors can omit a title and place a dismiss action beside the message. Keep failures actionable and scoped to the operation; a dismissed save error does not mean the data was saved. Do not retry mutations automatically or show raw provider errors or clinical content in shared feedback.

`ToastProvider` and `useToast` give the app one fixed, safe-area-aware notification viewport. It shows at most four messages at once and queues overflow in arrival order; dismissing or timing out a visible message promotes the next queued item. Success and information messages use polite status announcements; errors use assertive alerts. Transient messages default to five seconds, while `duration: 0` remains until explicitly dismissed. A caller-provided ID replaces its matching message, which supports stable persistent app errors. Toasts do not steal focus. Keep validation and recovery messages beside their owning workflow with `ErrorState` when a global toast would lose context. Give search inputs an explicit accessible label independent of placeholder text. `ToolbarSearch` supports a caller-owned clear action so feature query and pagination rules stay with the feature. Use the existing shared toolbar, filter, and loading compositions before adding variants; document behavior changes such as toast queueing, retry timing, or dismissal policy separately.

`Popover` composes Radix's nonmodal, portalled popover with the app's shared surface styling, viewport collision padding, and available-size constraints. Use it for anchored rich content such as template choices, draft history, and checkbox management; keep a menu's action semantics and a select's value semantics distinct. Provide an accessible label for the content, use a real button trigger, and let the primitive own Escape, outside dismissal, and focus restoration. Default z-order stays below modal content; a popover inside a dialog may opt into the dialog's local layer when its content must sit above that dialog.

`EmptyState` supports `section` (the existing default), `compact`, and `page` compositions. The owning workflow supplies accurate empty-state copy and actions for its cause; no-results states should offer a way to clear or adjust the relevant query/filter when that action is available.

The HTML bootstrap in `index.html` and React `LoadingScreen` use indeterminate loading bars with static reduced-motion feedback. The HTML bootstrap appears before React is available and needs its own inline styles. Privacy and terms modals are imported eagerly so their first opening shows the modal directly without a full-page fallback beside the application shell.

`src/components/ui/LoadingFeedback.tsx` provides a polite `LoadingIndicator`, a centered branded `LoadingScreen`, reduced-motion `Skeleton` shapes and a generic `ErrorState`. Compose these primitives in the feature that owns the pending content; keep available chrome visible and skeletonize only the pending region. Reuse app identity through `Brand`, `BrandMark`, and `BrandName`, use concise status text that describes the actual operation, and keep old valid results visible during refresh. Skeleton shapes are decorative and hidden from assistive technology. Feature imports use a lightweight feature-shaped fallback through `createLazyFeature`; successful lazy modules remain shared when navigating away and back.

Dashboard search/date controls and patient-scoped order/note filters retain their small UI values in memory while navigating during the current session. Keep clinical records, note drafts, and generated results in their existing feature/patient-store owners; do not add them to the generic view-state cache.

## Browser resource lifecycle

Recording/camera workflows use shared hooks for capture and stream cleanup; camera capture composes through `ModalShell` while retaining its stronger backdrop and explicit dismissal policy. File upload/drop workflows use existing conversion and preview ownership patterns. Stop media tracks, revoke object URLs, and clean up listeners/timers when their owner closes, is removed, or unmounts. Keep transcription or error behavior in the owning feature.

## Print and export surfaces

Prescription, home-instruction, and clipboard presentation paths retain feature-specific content. Preserve their meaning and formatting when changing shared UI; screen-only visual checks do not verify print or copied output.
